# 一、魔数与基本定位

你确定的魔数按以下 **4 个字节**写入文件开头：

| 文件偏移 | 十六进制 | 字符 |
|---|---:|---|
| `0x00` | `24` | `$` |
| `0x01` | `45` | `E` |
| `0x02` | `50` | `P` |
| `0x03` | `46` | `F` |

即：

```c
static const uint8_t EPF_MAGIC[4] = {
    0x24, 0x45, 0x50, 0x46
};
```

**磁盘中只有这 4 个字节，没有字符串结尾的 `\0`。** 与之相比，ELF 的魔数也占开头 4 字节，但其整个 `e_ident` 标识区占 16 字节；两者需要区分。[gabi.xinuos.com](https://gabi.xinuos.com/elf/02-eheader.html?utm_source=chatgpt.com)

EPF 可以暂定英文全称为 **Executable Program Format**。

建议覆盖三类文件：

| 类型值 | 名称 | 用途 | 建议扩展名 |
|---:|---|---|---|
| `1` | `EPF_REL` | 可重定位目标文件，供链接器使用 | `.epo` |
| `2` | `EPF_EXEC` | 可执行程序 | `.epf` |
| `3` | `EPF_SHARED` | 共享库 | `.eps` |

扩展名仅供工具和用户辨认，实际类型以文件头为准。

# 二、总体结构

EPF 保留两种视图：

- **装载视图：文件头 + 段表。** 告诉加载器如何建立内存映像。
- **链接视图：文件头 + 节表 + 符号表 + 重定位表。** 告诉链接器如何组合代码与数据。

ELF 本身也使用这两种视图：程序头表服务于执行，节头表服务于链接；用于执行的文件可以不包含节头表。这个分工很适合继续沿用。[gabi.xinuos.com](https://gabi.xinuos.com/elf/01-intro.html?utm_source=chatgpt.com)

EPF 中各部分的职责如下：

| 部分 | 职责 | 可执行文件运行时是否必需 |
|---|---|---|
| 文件头 | 格式、架构、ABI、入口、各表位置 | 必需 |
| 段表 | 内存映射、权限、运行时元数据位置 | 必需 |
| 代码与数据 | 程序内容 | 必需 |
| 动态目录 | 动态符号、依赖、运行时重定位 | 使用这些功能时必需 |
| 节表 | 描述链接和调试单位 | 可删除 |
| 静态符号表 | 静态链接、调试、分析 | 可删除 |
| 调试信息 | 调试器使用 | 可删除 |

这里应当确立一条核心规则：

> **执行一个已经链接完成的 EPF 文件，不得依赖节名或节表。**

段和节可以描述同一批文件字节，不需要把代码和数据保存两份。

# 三、基础编码与地址模型

<a id="epf-3-1"></a>

## 3.1 统一磁盘结构

建议 EPF v1 采用以下约定：

| 项目 | 规定 |
|---|---|
| 一个字节 | 8 bit |
| 元数据端序 | 小端 |
| 首版目标端序 | 小端 |
| 文件偏移 | `uint64_t` |
| RVA、映像大小 | `uint64_t` |
| 段数、节数、节索引 | `uint32_t` |
| 目标地址宽度 | 由 `address_size` 指定，取 `4` 或 `8` |
| 有符号重定位加数 | 小端、二进制补码 `int64_t` |
| 元数据表起点 | 至少 8 字节对齐 |

这样，**32 位和 64 位程序共用一套文件头、段表、节表和重定位结构**。区别体现在目标地址宽度及 ABI 上。

代价是 32 位小程序的元数据会稍大一些，但解析器和工具链可以少维护一套结构。

磁盘字段使用 64 位，并不意味着 32 位程序能使用任意 64 位地址。加载时仍须检查所有最终地址是否符合目标架构和进程地址空间限制。

<a id="epf-3-2"></a>

## 3.2 区分三种地址

EPF 明确区分：

| 名称 | 含义 |
|---|---|
| File Offset | 相对于文件开头的字节偏移 |
| RVA | 相对于当前映像基址的虚拟地址偏移 |
| VA | 程序运行时实际使用的虚拟地址 |

定义：

```text
B = 当前映像的实际装载基址

VA = B + RVA
```

不同文件的基址规则：

| 文件种类 | 基址规则 |
|---|---|
| 固定地址 `EXEC` | `B = image_base`，加载器必须使用指定基址 |
| PIE `EXEC` | 文件中 `image_base = 0`，加载器选择 `B` |
| `SHARED` | 文件中 `image_base = 0`，加载器选择 `B` |
| `REL` | 尚未形成运行时映像，相关字段为零 |

这里的 `B` 就是实际映像基址，不再引入另一套含义相近的“偏好基址差值”。

**静态链接/动态链接，与固定地址/PIE，是两组独立属性。** 静态 PIE 仍可能需要运行时重定位。

# 四、文件头：128 字节

建议文件头名称为 `EpfHeader`，v1.0 长度固定为 **128 字节**。

| 偏移 | 大小 | 字段 | 含义 |
|---:|---:|---|---|
| `0x00` | 4 | `magic` | `24 45 50 46` |
| `0x04` | 1 | `version_major` | 主版本，初始为 `1` |
| `0x05` | 1 | `version_minor` | 次版本，初始为 `0` |
| `0x06` | 1 | `address_size` | 目标地址宽度，`4` 或 `8` |
| `0x07` | 1 | `encoding` | v1 为 `1`，表示小端 |
| `0x08` | 2 | `type` | `REL / EXEC / SHARED` |
| `0x0A` | 2 | `machine` | CPU 架构编号 |
| `0x0C` | 2 | `os_abi` | 操作系统 ABI 编号 |
| `0x0E` | 2 | `abi_version` | 该 ABI 的版本 |
| `0x10` | 4 | `flags` | 文件属性 |
| `0x14` | 4 | `header_size` | v1.0 为 `128` |
| `0x18` | 8 | `required_features` | 必须支持的格式能力 |
| `0x20` | 8 | `image_base` | 固定地址程序的装载基址 |
| `0x28` | 8 | `entry_rva` | 程序入口 RVA |
| `0x30` | 8 | `image_size` | 映像预留虚拟地址范围大小 |
| `0x38` | 8 | `segment_table_offset` | 段表文件偏移 |
| `0x40` | 8 | `section_table_offset` | 节表文件偏移 |
| `0x48` | 8 | `file_size` | 文件总字节数 |
| `0x50` | 4 | `segment_count` | 段表项数量 |
| `0x54` | 4 | `section_count` | 节表项数量 |
| `0x58` | 4 | `shstr_index` | 节名字符串表的节索引 |
| `0x5C` | 2 | `segment_entry_size` | v1.0 为 `64` |
| `0x5E` | 2 | `section_entry_size` | v1.0 为 `64` |
| `0x60` | 8 | `map_align` | 映像布局采用的映射对齐粒度 |
| `0x68` | 4 | `arch_flags` | 由架构 ABI 定义的属性 |
| `0x6C` | 20 | `reserved` | v1.0 全部为零 |

<a id="epf-4-1"></a>

### 文件属性

第一版只定义一个 `flags` 位：

```c
#define EPF_F_PIE 0x00000001u
```

规则：

- `EXEC` 未设置 `PIE`：固定地址程序。
- `EXEC` 设置 `PIE`：位置无关可执行程序。
- `SHARED` 本身就具有可重定位映像语义，`PIE` 位保持为零。
- 未识别的属性位应拒绝，避免误解文件行为。

<a id="epf-4-2"></a>

### 必需能力

建议独立定义：

| 位 | 名称 | 含义 |
|---:|---|---|
| 0 | `RUNTIME_RELOC` | 需要运行时重定位 |
| 1 | `DYNAMIC_LINK` | 需要跨模块动态链接 |
| 2 | `TLS` | 需要线程局部存储 |
| 3 | `RELRO` | 需要重定位后只读保护 |

加载链不支持其中任何一个必需能力，就必须拒绝装载。

特别是，`RUNTIME_RELOC` 和 `DYNAMIC_LINK` 应分开：静态 PIE 可以只需要前者。

<a id="epf-4-3"></a>

### 入口与空表

规定：

```c
#define EPF_NO_ENTRY UINT64_MAX
```

这样 `entry_rva = 0` 仍然可以表示一个合法入口。

- `EXEC` 必须有有效入口。
- `REL` 和 `SHARED` 的 `entry_rva = EPF_NO_ENTRY`。
- 不存在某个表时，对应 `offset = 0`、`count = 0`。
- 没有节名字符串表时，`shstr_index = 0`。
- `REL` 的 `image_base`、`image_size`、`map_align` 为零。

<a id="epf-4-4"></a>

### 架构编号

`machine` 可以复用 ELF 的架构编号，减少工具链中的重复映射。例如：

| CPU | `machine` |
|---|---:|
| x86 32 位 | `3` |
| x86-64 | `62` |
| AArch64 | `183` |
| RISC-V | `243` |

这些编号来自 ELF 的机器类型注册表；EPF 只复用编号含义。[gabi.xinuos.com](https://gabi.xinuos.com/elf/a-emachine.html?utm_source=chatgpt.com)

`os_abi` 则需要 EPF 自己的注册规则。它必须能够区分不同操作系统的运行约定；仅知道 CPU 相同，还不足以执行程序。

# 五、段表：每项 64 字节

段表是加载器最重要的数据结构。

```c
typedef struct {
    uint32_t type;          // 0x00
    uint32_t flags;         // 0x04

    uint64_t file_offset;  // 0x08
    uint64_t rva;          // 0x10

    uint64_t file_size;    // 0x18
    uint64_t mem_size;     // 0x20

    uint64_t align;        // 0x28
    uint64_t reserved[2];  // 0x30
} EpfSegment;
```

这里的 C 定义用于说明字段。读写器应按规定的偏移和小端编码操作，不能把宿主编译器的结构体内存布局直接当作文件格式。

<a id="epf-5-1"></a>

## 5.1 段类型

| 值 | 名称 | 用途 |
|---:|---|---|
| `0` | `EPF_SEG_NULL` | 空项，其他字段为零 |
| `1` | `EPF_SEG_LOAD` | 建立内存映射 |
| `2` | `EPF_SEG_DYNAMIC` | 定位动态目录 |
| `3` | `EPF_SEG_INTERP` | 指定动态加载器 |
| `4` | `EPF_SEG_TLS` | 描述 TLS 初始化模板 |
| `5` | `EPF_SEG_RELRO` | 指定重定位后转为只读的范围 |
| `6` | `EPF_SEG_NOTE` | 附加元数据 |

**只有 `LOAD` 创建程序映射。** `DYNAMIC`、`TLS` 和 `RELRO` 是对相关内容或范围的补充描述，不再重复映射一份。

<a id="epf-5-2"></a>

## 5.2 段标志

```c
#define EPF_PF_R         0x00000001u
#define EPF_PF_W         0x00000002u
#define EPF_PF_X         0x00000004u
#define EPF_PF_REQUIRED  0x80000000u
```

低三位权限仅用于 `LOAD`。其他段类型的这三位必须为零。

基础规范规定：

- `LOAD` 必须可读。
- `W` 和 `X` 不得同时设置。
- 影响装载语义的段必须设置 `REQUIRED`。
- 遇到未知的必需段类型，加载器拒绝执行。
- 明确可忽略的附加元数据才能跳过。

<a id="epf-5-3"></a>

## 5.3 `LOAD` 的精确定义

对于一个 `LOAD`：

```text
文件内容：
    [file_offset, file_offset + file_size)

映射到：
    [B + rva, B + rva + file_size)

补零范围：
    [B + rva + file_size, B + rva + mem_size)
```

要求：

```text
0 <= file_size <= mem_size
mem_size > 0
```

这使 `.bss` 不需要占用实际文件字节。ELF 的可装载段也使用文件大小与内存大小的差值来表达零初始化区域。[gabi.xinuos.com](https://gabi.xinuos.com/elf/07-pheader.html?utm_source=chatgpt.com)

EPF 再明确一条容易遗漏的规则：

> **映射末尾不足一页时，页面中额外可见的字节也必须清零，不能暴露文件中紧随其后的其他内容。**

加载器可以先用匿名内存复制实现；优化时再直接映射完整文件页，对尾页使用私有副本并清零。

<a id="epf-5-4"></a>

## 5.4 对齐规则

设操作系统实际页大小为 `P`：

```text
map_align 是非零的 2 的幂
map_align % P == 0

每个 LOAD：
    align 是 2 的幂
    align >= map_align
    file_offset % align == 0
    rva % align == 0

实际基址 B：
    B % align == 0，适用于每个 LOAD
```

EPF 首版选择较严格的布局，以降低加载器复杂度：

- `LOAD` 按 RVA 升序排列。
- 两个 `LOAD` 的文件数据范围不得重叠。
- 两个 `LOAD` 按 `map_align` 向外取整后的虚拟范围不得重叠。
- 映像中没有段覆盖的完整页面保持不可访问。
- 系统页大小不满足文件要求时，拒绝装载。

映像大小定义为：

```text
image_size =
    align_up(max(LOAD.rva + LOAD.mem_size), map_align)
```

不支持“改变分页参数后勉强加载”这样的隐式转换。

<a id="epf-5-5"></a>

## 5.5 其他段的约束

| 段 | 主要约束 |
|---|---|
| `DYNAMIC` | 最多一个；内容位于可读 `LOAD` 的已初始化文件范围内，文件偏移与 RVA 必须对应 |
| `INTERP` | 最多一个；内容为单个有结尾 NUL 的路径；路径解释由 OS ABI 规定 |
| `TLS` | 最多一个；描述每线程初始化数据和零填充长度 |
| `RELRO` | 只描述权限变更范围；覆盖完整映射页；重定位完成后变为只读 |
| `NOTE` | 不影响执行的附加信息可标为非必需 |

`RELRO` 与 `LOAD` 重叠是正常的；禁止重叠的规则针对两个独立的 `LOAD` 映射。

# 六、节表：每项 64 字节

节表服务于编译、链接、调试和分析。

```c
typedef struct {
    uint32_t name_offset;
    uint32_t type;

    uint64_t flags;
    uint64_t rva;
    uint64_t file_offset;
    uint64_t size;

    uint32_t link;
    uint32_t info;

    uint64_t align;
    uint64_t entry_size;
} EpfSection;
```

<a id="epf-6-1"></a>

## 6.1 节类型

以下为 EPF 自己的节类型编号：

| 值 | 名称 | 用途 |
|---:|---|---|
| `0` | `EPF_SHT_NULL` | 空节 |
| `1` | `EPF_SHT_PROGBITS` | 代码或普通数据 |
| `2` | `EPF_SHT_NOBITS` | 仅占内存的零初始化数据 |
| `3` | `EPF_SHT_STRTAB` | 字符串表 |
| `4` | `EPF_SHT_SYMTAB` | 静态符号表 |
| `5` | `EPF_SHT_RELA` | 显式加数重定位表 |
| `6` | `EPF_SHT_DYNSYM` | 动态符号表 |
| `7` | `EPF_SHT_NOTE` | 附加元数据 |
| `8` | `EPF_SHT_DYNAMIC` | 动态目录 |

如果节表存在，第 `0` 项必须全零，实际节从索引 `1` 开始。

节属性可以定义为：

```c
#define EPF_SHF_ALLOC     0x0000000000000001ull
#define EPF_SHF_WRITE     0x0000000000000002ull
#define EPF_SHF_EXEC      0x0000000000000004ull
#define EPF_SHF_TLS       0x0000000000000008ull
#define EPF_SHF_REQUIRED  0x8000000000000000ull
```

<a id="epf-6-2"></a>

## 6.2 字段语义

- `name_offset`：节名在节名字符串表中的字节偏移。
- `rva`：已链接映像中该节的 RVA；`REL` 和非装载节填零。
- `size`：节内容大小；对 `NOBITS` 表示内存大小。
- `NOBITS.file_offset = 0`，没有对应文件内容。
- `align`：内容对齐要求，非空普通节为非零的 2 的幂。
- `entry_size`：表格型节的单项长度；普通字节数据填零。

关联字段规定：

| 节类型 | `link` | `info` |
|---|---|---|
| `SYMTAB` / `DYNSYM` | 对应字符串表的节索引 | `0` |
| `RELA` | 对应符号表的节索引 | 被修改的目标节索引 |
| 其他基础类型 | `0` | `0` |

对于带 `ALLOC` 的已链接节，其描述必须与所属 `LOAD` 一致，不能出现节表说一个地址、段表说另一个地址的情况。

`.text`、`.rodata`、`.data`、`.bss` 等名称只是约定。加载器依赖类型、范围和权限，不根据节名决定行为。

<a id="epf-7"></a>

# 七、符号表：每项 32 字节

建议为符号增加一个独立的**定义域字段**，明确 `value` 到底表示什么。

```c
typedef struct {
    uint32_t name_offset;
    uint32_t section_index;

    uint64_t value;
    uint64_t size;

    uint8_t binding;
    uint8_t type;
    uint8_t visibility;
    uint8_t domain;

    uint32_t reserved;
} EpfSymbol;
```

<a id="epf-7-1"></a>

## 7.1 定义域

| `domain` | 值 | `value` 的含义 | `section_index` |
|---|---:|---|---|
| `UNDEF` | `0` | 未定义，必须为零 | `0` |
| `SECTION` | `1` | 相对所属节起点的偏移 | 有效节索引 |
| `IMAGE` | `2` | 相对映像基址的 RVA | `0` |
| `ABS` | `3` | 不随装载基址变化的绝对数值 | `0` |
| `TLS` | `4` | TLS 模块内偏移 | 由 TLS ABI 规定 |

解析规则：

```text
SECTION:
    最终地址 = 链接器分配给该节的地址 + value

IMAGE:
    最终地址 = 当前模块的实际基址 + value

ABS:
    最终数值 = value
```

**运行时动态符号禁止使用 `SECTION` 定义域。**

这样，即使节表已经删除，动态链接器仍能判断符号是否定义、如何取得地址。

<a id="epf-7-2"></a>

## 7.2 其他属性

```text
binding:
    0 = LOCAL
    1 = GLOBAL
    2 = WEAK

type:
    0 = NOTYPE
    1 = OBJECT
    2 = FUNC
    3 = SECTION
    4 = TLS

visibility:
    0 = DEFAULT
    1 = HIDDEN
```

符号索引 `0` 保留为全零空符号。真正的未定义外部符号使用索引大于零、带名称的 `UNDEF` 条目。

静态链接规则建议确定为：

- `LOCAL` 只在所属目标文件内有效。
- 多个同名强定义报错。
- 强定义覆盖弱定义。
- 多个弱定义按链接输入顺序选择。
- 未解析强引用报错。
- 未解析弱引用取绝对值零。

字符串表使用 NUL 结尾的字节串，名称按原始字节精确匹配。由于名称偏移为 `u32`，单个相应字符串表最多为 4 GiB，解析器还可以设置更低的资源上限。

# 八、重定位表：每项 32 字节

EPF 建议统一使用显式加数，不再另设隐式加数格式。ELF 的 `REL` 与 `RELA` 的主要区别之一，就是加数保存在被修改位置还是保存在重定位条目中。[ELF Object File Format 4.2 documentation](https://gabi.xinuos.com/v42/elf/06-reloc.html?utm_source=chatgpt.com)

```c
typedef struct {
    uint64_t offset;
    int64_t  addend;

    uint32_t symbol_index;
    uint32_t type;

    uint64_t reserved;
} EpfRela;
```

`offset` 的解释取决于文件类型：

| 文件 | `offset` 含义 |
|---|---|
| `REL` | 相对目标节起点的字节偏移 |
| `EXEC` / `SHARED` | 被修改位置的 RVA |

定义：

```text
S = 已解析的符号地址或绝对数值
A = 显式 addend
P = 被修改位置的最终地址
B = 当前映像实际装载基址
```

可以先定义以下通用数据重定位：

| 类型值 | 名称 | 写入内容 |
|---:|---|---|
| `0` | `NONE` | 不写入 |
| `1` | `ABS32` | 32 位无符号 `S + A` |
| `2` | `ABS64` | 64 位无符号 `S + A` |
| `3` | `PCREL32` | 32 位有符号 `S + A - P` |
| `4` | `RELATIVE32` | 32 位无符号 `B + A` |
| `5` | `RELATIVE64` | 64 位无符号 `B + A` |

规定：

- `RELATIVE32/64` 的 `symbol_index` 必须为零。
- 运算应检查溢出，不能直接截断。
- 写入的**整个范围**必须位于合法目标区域内。
- 基础运行时重定位只允许修改可写数据或待转为只读的 RELRO 区域。
- 首版不允许修改可执行代码的运行时重定位。
- 基础格式不允许两个重定位产生重叠写入。

这些通用类型用于连续整数存储单元。涉及 CPU 指令位域的重定位，例如分支立即数、拆分高低位、配对重定位，应由架构 ABI 分配独立类型并定义编码规则。

`PCREL32` 中的 `P` 是被修改字段的地址；如果具体指令相对“下一条指令”计算位移，需要由对应的加数或架构重定位规则补偿。

# 九、动态链接设计

动态链接器必须仅凭段表和动态目录完成工作，不能依赖节表。

<a id="epf-9-1"></a>

## 9.1 动态目录项

```c
typedef struct {
    uint32_t tag;
    uint32_t flags;
    uint64_t value;
} EpfDynamicEntry;
```

每项 **16 字节**。

建议定义：

| Tag | 名称 | `value` 含义 |
|---:|---|---|
| `0` | `NULL` | 目录结束 |
| `1` | `STRTAB_RVA` | 动态字符串表 RVA |
| `2` | `STRSZ` | 字符串表字节数 |
| `3` | `SYMTAB_RVA` | 动态符号表 RVA |
| `4` | `SYMCNT` | 符号数量 |
| `5` | `SYMENT` | 符号项长度，v1 为 `32` |
| `6` | `RELA_RVA` | 运行时重定位表 RVA |
| `7` | `RELACNT` | 重定位数量 |
| `8` | `RELAENT` | 重定位项长度，v1 为 `32` |
| `9` | `NEEDED` | 依赖名称在动态字符串表中的偏移 |
| `10` | `SONAME` | 当前模块名称的字符串表偏移 |
| `11` | `INIT_ARRAY_RVA` | 初始化函数数组 RVA |
| `12` | `INIT_COUNT` | 初始化函数数量 |
| `13` | `FINI_ARRAY_RVA` | 结束函数数组 RVA |
| `14` | `FINI_COUNT` | 结束函数数量 |

其中：

- `*_RVA` 是 RVA。
- `NEEDED`、`SONAME` 是字符串表内偏移。
- `SYMCNT`、`RELACNT` 是数量。
- 不能把它们统一当作指针加上基址。

必要约束：

1. 动态目录的文件大小为 16 的倍数。
2. 必须在段边界内出现 `NULL`。
3. `NULL` 的其他字段为零，后续只允许全零填充。
4. 一组表的地址、数量、项长字段必须完整出现。
5. 除 `NEEDED` 外，基础单例 Tag 不得重复。
6. 所有运行时表都必须位于可读 `LOAD` 的已初始化内容中。
7. `flags` 的 bit 0 表示 `REQUIRED`；未知必需 Tag 必须拒绝。
8. 运行时重定位不得覆盖动态目录、符号表、字符串表及重定位表本身。

初始化数组和结束数组统一保存 **小端 `u64 RVA`**，调用地址为 `B + RVA`。数组本身不再进行指针重定位。

<a id="epf-9-2"></a>

## 9.2 第一版动态绑定规则

为了让行为明确、实现规模可控，建议 EPF 第一版采用：

- 启动时完成全部符号绑定和重定位。
- 模块内已定义符号绑定本模块。
- 外部 `UNDEF` 符号在该模块的依赖闭包中查找。
- 查找顺序由 `NEEDED` 顺序确定，按广度优先遍历并去重。
- 只考虑依赖中 `DEFAULT` 可见的 `GLOBAL/WEAK` 导出。
- 优先取顺序中第一个强定义；没有强定义时取第一个弱定义。
- 未解析强引用报错，未解析弱引用取零。
- 第一版依赖图必须无环；循环在任何初始化发生之前报错。

模块初始化按依赖先于使用者的顺序进行；同层次以首次发现顺序确定先后。模块内 INIT 数组正序调用，FINI 数组逆序调用，模块间结束处理按实际初始化顺序的逆序进行。

库文件查找路径、模块唯一身份和 ABI 兼容检查由 OS ABI 定义。不能仅因为两个文件具有相同 `SONAME` 就认定它们是同一个模块。

这套规则构成 **EPF 自己的动态绑定语义**。迁移现有程序时，工具链必须遵守这些规则。

<a id="epf-9-3"></a>

## 9.3 谁负责运行时重定位

责任必须唯一：

| 情况 | 负责者 |
|---|---|
| 没有 `INTERP`，也没有运行时重定位 | EPF 加载器直接完成装载 |
| 没有 `INTERP`，仅需基础 `RELATIVE32/64` | 支持 `RUNTIME_RELOC` 的 EPF 加载器 |
| 存在 `INTERP` | 动态加载器负责所有运行时重定位 |

有解释器时，系统先进入解释器，传递主程序基址、入口和段信息；解释器完成准备后再进入主程序。

无解释器的静态程序，其初始化函数由用户态启动代码执行。内核加载器不负责调用用户程序的构造函数。

# 十、一个具体装载示例

假设一个 x86-64 固定地址静态程序：

```text
type                 = EPF_EXEC
address_size         = 8
machine              = 62
flags                = 0
required_features    = 0

image_base           = 0x00400000
entry_rva            = 0x00001000
map_align            = 0x00001000
image_size           = 0x00005000

segment_table_offset = 0x80
segment_count        = 3

section_table_offset = 0
section_count        = 0

file_size            = 0x3180
```

目标 OS ABI 由该系统另行约定。

三个装载段：

| 段 | 文件偏移 | RVA | 文件大小 | 内存大小 | 权限 |
|---|---:|---:|---:|---:|---|
| 代码 | `0x1000` | `0x1000` | `0x680` | `0x680` | `R-X` |
| 只读数据 | `0x2000` | `0x2000` | `0x2C0` | `0x2C0` | `R--` |
| 可写数据 | `0x3000` | `0x3000` | `0x180` | `0x1800` | `RW-` |

每个段的 `align = 0x1000`。

由此得到：

| 内容 | 运行时范围或地址 |
|---|---|
| 代码起点 | `0x00401000` |
| 只读数据起点 | `0x00402000` |
| 已初始化可写数据 | `[0x00403000, 0x00403180)` |
| 零初始化区域 | `[0x00403180, 0x00404800)` |
| 程序入口 | `0x00401000` |

其中 `.bss` 对应的零初始化区域大小为：

```text
0x1800 - 0x180 = 0x1680 字节
```

它不需要占用文件字节。

文件头与段表总共占用：

```text
128 + 3 × 64 = 320 字节 = 0x140
```

本例中它们不映射进程序地址空间，首个映像页面也保持不可访问。最后一个可写页面中，`0x00404800` 至页末的额外可见字节清零。

**这个文件完全没有节表，仍然具备执行所需的全部装载信息。**

# 十一、加载器的基本流程

基础加载器可以按以下顺序实现：

1. **读取并检查文件头。**  
   检查魔数、版本、编码、架构、ABI、必需能力和实际文件长度。

2. **读取并校验段表。**  
   检查表范围、数量、步长、所有段范围、对齐和权限组合。

3. **确定实际基址。**  
   固定程序使用 `image_base`；PIE 和共享库选择满足全部对齐要求的基址。

4. **预留映像范围并建立映射。**  
   根据 `LOAD` 放置文件内容，清零尾部和零初始化区域，保留空洞。

5. **处理重定位及相关运行时要求。**  
   根据有无 `INTERP` 将责任交给正确的加载组件。

6. **落实最终内存权限。**  
   完成 RELRO 保护；整个过程中不得出现同时可写、可执行的页面。

7. **构造进程启动状态。**  
   栈、参数、环境、辅助信息、线程状态等由目标 OS ABI 规定。

8. **转移控制权。**  
   进入解释器入口或程序入口。

入口地址必须落在可执行 `LOAD` 的**文件内容范围**内，不能只落在其零填充区域内，还必须满足架构的指令对齐要求。

<a id="epf-11-1"></a>

## 必须采用无溢出的范围检查

例如，文件范围检查应写成：

```text
offset <= actual_file_size
size <= actual_file_size - offset
```

表范围检查：

```text
table_offset <= actual_file_size
entry_size != 0
count <= (actual_file_size - table_offset) / entry_size
```

内存范围检查：

```text
rva <= image_size
mem_size <= image_size - rva
```

`align_up`、地址加法和乘法也必须检查溢出。实现还应为段数、节数、映像大小和依赖数量设置明确资源上限。

# 十二、版本兼容与实现边界

<a id="epf-12-1"></a>

## 12.1 版本规则

建议采用以下兼容策略：

- 不认识的主版本：拒绝。
- 更高次版本：只有已知前缀可解析、必需能力受支持、未知内容允许忽略时，才能继续。
- 表项按文件声明的步长遍历，不能始终使用宿主的 `sizeof`。
- v1.0 的保留字段必须为零。
- 改变执行含义的扩展必须通过必需能力或明确的必需条目声明。
- 未知架构属性、重定位类型和必需语义必须报错，不能猜测解释。

<a id="epf-12-2"></a>

## 12.2 配套 ABI 需要单独定义

EPF 文件结构本身无法替代平台 ABI。每个可运行的平台组合还需要规定：

| 内容 | 原因 |
|---|---|
| 程序入口时的寄存器与栈布局 | `_start` 必须知道如何接收参数 |
| 函数调用约定 | 模块之间需要正确传递参数与返回值 |
| 系统调用约定 | 程序需要使用操作系统服务 |
| 架构专用重定位 | 指令编码和位域不同 |
| TLS 布局与线程指针 | TLS 不能当作普通 RVA 数据处理 |
| 异常展开和运行时登记 | 支持相应语言运行时 |
| 动态加载器交接协议 | 主程序信息必须可靠传给解释器 |
| CPU 扩展与 `arch_flags` | 避免在不支持的 CPU 上执行 |

第一版可以先实现不使用 TLS、异常展开和复杂动态链接的静态程序。涉及这些能力的文件必须明确声明需求，基础实现遇到它们应返回“不支持该能力”。

<a id="epf-12-3"></a>

## 12.3 建议的实现顺序

最合适的落地顺序是：

1. **固定地址静态 `EXEC`**：实现文件头、`LOAD`、入口和权限，先建立完整执行链。
2. **`REL` 与静态链接器**：加入节、符号、显式加数重定位。
3. **静态 PIE**：加入基址选择和 `RELATIVE32/64`。
4. **共享库与动态加载器**：实现动态目录、依赖、导入导出和 RELRO。
5. **平台扩展**：补充 TLS、异常展开、调试及更多架构重定位。

**这份方案最适合先冻结的核心是：4 字节 `$EPF` 魔数、128 字节文件头、64 字节段与节描述符、统一小端编码、RVA 地址模型，以及运行时不依赖节表的原则。** 这些确定后，静态加载器可以先工作，后续链接和运行时能力也有清晰的扩展位置。
